## Executive Summary

This security audit identified **18 findings** across a Laravel-based cryptocurrency exchange platform. After evidence-chain verification, **16 findings are confirmed** and **2 are rated as highly likely** pending deployment configuration verification.

**Severity distribution of confirmed findings:**
- **Critical:** 5 — Unauthenticated RCE, deposit callback signature bypass, 2FA bypass, withdrawal self-approval, recharge self-approval
- **High:** 7 — Non-idempotent withdrawal refund, negative amount fund transfer, mass assignment across all models, bypassable CAPTCHA, IP spoofing/fatal error, insufficient rate limiting, deprecated PHP function fatal error
- **Medium:** 4 — CSRF disabled globally, hardcoded API credentials, missing security headers, deposit address data leak

**Likely findings (2):** Debug-mode SMS bypass in registration, hardcoded fallback secret for wallet callback — both depend on production configuration that cannot be verified from source alone.

The most critical attack surface is the **financial operations layer**, where multiple authorization bypass and callback verification failures enable direct balance inflation. The user-facing `withdraw_dispose` and `recharge_dispose` endpoints accept user-controlled status parameters without admin authorization, allowing any authenticated user to approve their own transactions. Combined with the non-halting signature verification on the Udun deposit callback and the non-idempotent refund logic, an attacker has multiple independent paths to inflate wallet balances.

The platform also has systemic code-level weaknesses: all Eloquent models use `$guarded = []` (mass assignment), CSRF protection is globally disabled, security headers are absent, and a legacy `eregi()` call causes a fatal error on the required PHP 7.3+ runtime.

### RC-001-REV-001 — Unauthenticated Remote Code Execution via WebHook Deploy Endpoint

| Field | Detail |
|---|---|
| **Severity** | Critical |
| **Bound Function** | Deployment Operations (unmapped to feature taxonomy) |
| **Entry Point** | `POST /hook_deploy` — `routes/web.php:26` |
| **Sink / Risk Point** | `shell_exec("cd $path && git pull >> {$log_path}")` — `app/Http/Controllers/WebHook.php:23` |
| **Control Failure** | Token authentication completely commented out (`WebHook.php:17-21`); CSRF middleware globally disabled (`Kernel.php:46`) |

**Evidence & Data Flow:**
1. **Source:** Route registered at `routes/web.php:26` — `Route::post('hook_deploy', 'WebHook@deploy');` — no authentication middleware.
2. **Transit:** Controller at `WebHook.php:11-25` — `$path = base_path()` assigned; token check commented out at lines 17-21; shell command constructed from server path.

**Why It Stands:** The evidence chain is fully closed. The endpoint is completely unauthenticated. Any external attacker can trigger server-side `git pull` by sending a POST request. If the git remote is attacker-controlled or the repository contains malicious code, this is full RCE.

**Remediation:**

### RC-002-REV-001 — Udun Deposit Callback Signature Verification Not Enforced

| Field | Detail |
|---|---|
| **Severity** | Critical |
| **Bound Function** | Financial Operations → Wallet/Deposit → Deposit Processing (BF-002 / SF-014 / CF-001) |
| **Entry Point** | `POST /api/udun/notify` — `routes/yx_api.php:14` |
| **Sink / Risk Point** | `UdunDeposit::dispatch($trade)->onQueue('UdunDeposit')` credits user balance — `UdunWalletController.php:36-38`, `UdunDeposit.php:108-109` |
| **Control Failure** | Signature check logs mismatch but does not halt execution; hardcoded fallback API key `a0cd2e9a2a50b2682b198b5f6ff9b9b0` |

**Evidence & Data Flow:**
1. **Source:** `routes/yx_api.php:14` — `$api->any('udun/notify', 'UdunWalletController@notify');` — registered without `auth.api` middleware.
2. **Transit:** `UdunWalletController.php:26-29` — signature computed via `md5($body . config('coin.api_key', '<hardcoded>') . $nonce . $timestamp)`; mismatch only logged via `info('验签失败', $res)` with no return/break.
3. **Sink:** `tradeType==1 && status==3` triggers `UdunDeposit::dispatch()` which looks up wallet by address and credits `usable_balance` via `update_wallet_and_log`.

**Why It Stands:** The signature verification does not halt execution on failure. Combined with the hardcoded fallback secret visible in source code, an attacker can forge deposit callbacks to credit arbitrary wallets without actual blockchain deposits.

**Business Impact:** Direct balance inflation. Attacker can credit any user's wallet with fabricated deposit amounts, then withdraw real funds.

**Remediation:**
- Add `return` or `abort()` on signature mismatch to halt execution immediately.
- Remove hardcoded fallback API key; require `coin.api_key` from environment configuration.
- Add idempotency checks on deposit `txid` to prevent duplicate processing.

### RC-003-REV-001 — Non-Idempotent Withdrawal Refund via Callback Replay

| Field | Detail |
|---|---|
| **Severity** | High |
| **Bound Function** | Financial Operations → Withdrawal → Callback Processing (BF-002 / SF-014 / CF-002) |
| **Entry Point** | `POST /api/udun/notify` with `tradeType=2` — `routes/yx_api.php:14` |
| **Sink / Risk Point** | `User::find($user_id)->update_wallet_and_log(...)` at `UdunWalletController.php:57,64` |
| **Control Failure** | No check on `withdraw.status` before applying refund; no idempotency key on refund operations |

**Evidence & Data Flow:**
1. **Source:** `UdunWalletController.php:40-66` — withdrawal callback path.
2. **Transit:** `Withdraw::find($withdrawId)` retrieves withdrawal record; status=2 (rejected) or status=4 (failed) triggers `update_wallet_and_log` without checking current withdrawal state.
3. **Sink:** Each replay of a status=2 or status=4 callback credits the user's `usable_balance` again by the full withdrawal amount.

**Why It Stands:** The controller does not verify whether the withdrawal is already in rejected/failed state before applying the refund. Replaying the same callback causes repeated balance credits.

**Business Impact:** An attacker who can intercept or replay Udun callbacks (or forge them using RC-002) can multiply their balance by replaying withdrawal rejection callbacks.

**Remediation:**
- Check `withdraw.status` is in an appropriate pending state before applying refund.
- Add a unique constraint or idempotency key on refund operations.
- Combine with the signature enforcement fix from RC-002.

### RC-011-REV-001 — IP Spoofing via X-Forwarded-For + Fatal Error from Deprecated eregi()

| Field | Detail |
|---|---|
| **Severity** | High |
| **Bound Function** | User Management → Infrastructure (BF-001 / SF-012) |

When `config('app.debug')` is `true` AND the submitted code is `'0000'`, SMS verification is entirely skipped.

**Highly Suspect Reason:** The code bypass path is clearly present and functional. The `.env.example` file suggests debug-friendly defaults. The bypass enables mass account creation with arbitrary phone numbers.

**Missing Key Evidence:** Whether production deployments set `APP_DEBUG=false`. The `.env.example` is not definitive proof of production configuration.

**Upgrade to Confirmed:** Verify that `APP_DEBUG=true` in any production `.env` file, or confirm that the debug bypass is reachable in a deployed instance.

**Business Impact (if active):** Mass account creation without SMS verification. Enables attacker to create unlimited accounts for wash trading, bonus abuse, or Sybil attacks.

**Remediation:**
- Remove the debug-mode SMS bypass entirely from production code paths.
- Use environment-specific feature flags that cannot be toggled by `APP_DEBUG`.

### RC-018-REV-001 — Hardcoded Fallback Secret for Wallet Callback

| Field | Detail |
|---|---|
| **Severity** | High (compounded by RC-002) |
| **Bound Function** | Financial Operations → Wallet/Deposit (BF-002 / SF-014 / CF-001) |
| **Entry Point** | `POST /api/udun/notify` — `UdunWalletController.php:26` |

**Current Evidence:**
The Udun callback controller uses:
```php
config('coin.api_key', 'a0cd2e9a2a50b2682b198b5f6ff9b9b0')
```
The hardcoded fallback key `a0cd2e9a2a50b2682b198b5f6ff9b9b0` is used when `coin.api_key` config is missing.

**Highly Suspect Reason:** The hardcoded key is confirmed in source. The `config/` directory is absent from the distributed archive, making it likely that the fallback is used. However, the primary vulnerability (RC-002: signature check doesn't halt on failure) makes the key's value secondary — the check is bypassed regardless.

**Missing Key Evidence:** Whether `coin.api_key` is set in the actual deployment configuration. The missing `config/` directory is a strong indicator but not definitive proof.

**Upgrade to Confirmed:** Verify that the `coin.api_key` configuration value is not set in production, or confirm the config directory absence in the deployment environment.

**Business Impact:** If the fallback key is used, an attacker knowing this default value (visible in source code) can forge valid callback signatures. Combined with RC-002, this is fully exploitable regardless.

**Remediation:**
- Remove the hardcoded fallback key; fail loudly if `coin.api_key` is not configured.
- Rotate the exposed key immediately.
